Lingxi灵犀

Repository-Level Issue Resolution Framework Enhanced by Procedural Knowledge Guided Scaling

有经验的开发者在动手探索之前，心里已经有数：一类问题该怎么诊断、怎么修，以及为什么。灵犀从仓库自身的历史中恢复这种过程性知识，并把它摆到 coding agent 面前，让分析、规划和修复都沿着适合当前 issue 的过程进行。

01 · 动机

隐性知识告诉开发者该往哪里看。

有经验的开发者面对一个 issue，是怎么入手的？在开始探索之前，他们其实已经知道一些东西。

在学习和工作中，开发者自然积累了隐性知识：某一类问题该怎么理解、怎么分析、怎么解决。新问题很少和旧问题完全一样，所以他们会从很多过去的案例里抽出几个共通的模式，由这些模式一起决定先去哪里看。知识在前，探索在后。

有经验的开发者

借助过去案例的共通之处

从一个慢页面出发，可以走的路有很多。开发者只走其中一条：经过视图和 ORM，找到逐条发出的查询，并且很早就排除了一条岔路。编号的几步就是过程；而“为什么”让这个过程能用到下一个慢页面上，哪怕换了一个代码库。这就是过程性知识：一类问题怎么诊断、怎么修，以及为什么。它是隐性的：存在于经验里，不在代码里。

过程性知识

当页面加载很慢时：

  1. 1数一数数据库查询的次数
  2. 2找到发出这些查询的循环
  3. 3在查询日志里确认

为什么逐条查询，即 N+1 问题，是常见原因。

今天的 coding agent 如何探索

同样的情境下，coding agent 带着三样东西

1
模型自身的知识

存在权重里的通用编程经验：很强，而且每一代模型都在变强。

2
当前的代码仓

它现在的代码和文档。

代码库与文档
3
探索与遍历

采样、分支、重试：很多条轨迹。

③ 借助 ① 去探索 ②。那么问题来了：面对这个 issue，对的那条经验会被想起来吗？

今天的 agent 缺什么

不一定，原因有两个。

现在的 agent 在一般意义上很会探索。但有两件事，让这种探索没能沿着适合当前 issue 的过程进行。

缺少针对任务的方向 ③ 探索

会探索，但不知道这个 issue 最好怎么探索

模型在大量代码上训练过，已经大体知道怎样探索一个代码仓：搜索、阅读、复现、测试。它无法事先知道的，是在这个代码仓里，这个任务最好怎么入手：该用哪条实践，先检查什么，修改又要怎样和现有代码契合。

没有什么能保证对的实践在对的时刻被想起来，而私有代码库本来就不在训练数据里。于是提升只能靠多试：更多采样，更多重试。覆盖面变大了，针对这个 issue 的方向却没有。

相关工作：测试时扩展，先采样大量候选补丁再从中挑选，例如 Trae、DARS、DEI。

停留在表面 过程性知识

没有过程性知识，或只把历史当原始数据用

很多 agent 完全不用：它们只依据现在的代码和文档工作，而这些只记录了当前状态，没有记录类似的 issue 当初是怎么处理的。用到历史的那些，也只是把它当原始数据：以文本形式检索过去的 issue 报告和补丁。改了什么保留了下来，背后的过程却丢了：这个 issue 是怎么诊断的，为什么这样修。

照搬的修改只有在新 issue 几乎一模一样时才有用。真正能迁移的，是修改背后的过程。

Issue 报告

  • 怎么诊断的根因分析步骤
  • 为什么这样修修复模式

相关工作：使用当前代码仓的代码图和 AST，例如 Agentless、AutoCodeRover、CGM；以文本形式使用相似的历史 issue，例如 SemAgent。

灵犀做了什么灵犀从代码仓自己的历史 issue 和补丁中恢复过程，把它抽象成能迁移到类似 issue 的知识；新 issue 到来时，再把相关的部分摆到 agent 面前。过去的修复是知识的来源，agent 拿到的是过程。
02 · 方法

离线恢复过程，引导每一个新 issue。

灵犀分三个阶段。阶段 1 对每个代码仓的历史只运行一次；阶段 2 和 3 针对每个新 issue 运行：检索到的知识先引导分析，再引导规划和修复。

1阶段 1 · 离线知识构建

从针对具体 issue 到可迁移的知识。

一次历史修复只留下两样东西：issue 报告和最终补丁，中间的过程是缺失的。知识 agent 分两步把它找回来。第一步做逆向推理：从补丁出发，浏览 issue 发生时的代码仓快照，解释每一处修改为什么能修好这个 issue。第二步把结果抽象化，使它能迁移到相似但不完全相同的 issue 上。

知识按代码仓、从它自己的历史中构建；对每个目标 issue，只使用在它之前创建的 issue。

通用根因分析步骤 · 同一个 issue · 第二步
  1. "Identify the request handling flow and URL resolution process
  2. Review how URL configuration is managed during request processing
  3. Analyze object creation patterns and resource usage
  1. Check for performance optimization opportunities like caching/memoization
  2. Verify thread-safety and resource cleanup mechanisms
  3. Test behavior with different URL configuration scenarios"

这个 issue：每个请求都新建一个 URL resolver，而不是复用已缓存的那个，白白浪费内存和时间。第一步点名了具体的类和被绕过的带缓存函数。第二步把它变成了在任何代码库里诊断类似问题的方法：顺着请求流程走，看看每次请求都创建了哪些对象，再检查是否有现成的缓存被绕过。

2阶段 2 · 知识引导的分析扩展

每个分析 agent 一份知识。

新 issue 到来后，灵犀先把它总结成四个字段，再检索相似历史 issue 的知识：向量检索保留前 20 个，重排模型排序后，保留最相关的 3 个。

为什么一个 agent 只给一份知识？如果把检索到的知识都塞进一个长提示里，模型往往会丢掉埋在中间的内容。所以每份知识各自引导一个分析 agent：三份知识，三个 agent，各自沿着不同的过程分析，各写一份报告。分析综合再保留其中有支撑、互补、准确、完整的部分，形成一份综合分析。相关知识不再靠模型自己想起来，而是直接摆到 agent 面前。

3阶段 3 · Issue 解决

用分析结果和 issue 修复知识来规划和修复。

分析说明了哪里出了问题；阶段 3 用两个 agent 把它变成补丁。检索到的知识中与修复相关的部分，同时引导这两个 agent。

规划 agent

探索 → 复现 → 规划

参考分析结果和 issue 修复知识，给出根因判断和精确到行的修改计划。它会探索代码、复现 issue，并把每一处计划中的修改和它要解决的问题对应起来。

修复 agent

实现 → 测试 → 完善

实施修改，运行复现测试，不断完善直到测试通过，得到最终补丁。检查清单告诉它要验证什么。两个 agent 都使用四个工具：目录查看、文件查看、关键词搜索和字符串替换编辑器。

03 · 实验评估

效果如何？哪类知识最有用？

所有实验都在 SWE-bench Verified 上进行：来自 12 个开源 Python 项目的 500 个真实 GitHub issue，每个都由隐藏测试检验。 Pass@1 是单次生成的补丁通过测试的 issue 比例。对每个目标 issue，知识只来自在它之前创建的 issue。

商用模型的实验均在 2025 年 9 月前完成
RQ1 · 整体效果

在相同基础模型下，灵犀解决的 issue 最多。

怎么看每组使用同一个基础模型，所以组内唯一的区别是框架。基线是排行榜上使用同一基础模型的领先方法，不包括多模型集成。

说明了什么使用 Claude 4 Sonnet 时，灵犀达到 74.6%，比最强的对比框架 OpenHands 和 Augment v1（70.4%）高 4.2 个百分点。使用 Kimi-K2 时为 70.3 对 65.4。使用 GPT-4.1 mini 时，灵犀几乎是 mini-SWE-agent 的两倍：45.2 对 23.9。跨组来看，更强的模型让同一框架的成绩更高（红线），而灵犀在每一组都排第一。知识是在模型之上的补充，而不是替代。

怎么看提升来自知识，还是来自并行的多个 agent？每一行去掉或替换灵犀的一个部分。这 218 个 issue 是统计抽样（95% 置信度，5% 误差范围）。

说明了什么没有知识时，Pass@1 为 67.4 到 67.7。使用原始 issue–patch 对，也就是只有修复、没有过程，达到 68.3。可迁移的过程性知识带来最大的一步，到 74.8。并行分析在此基础上发挥作用：有知识时，它再带来 2.3 个百分点，因为每一路都沿着自己的那份知识分析，结论再合在一起；没有知识时，对同一份 issue 报告做多路并行分析，结果和单路分析接近。两者相互配合。

这里的差值是绝对百分点；论文表 3 用相对 Δ 报告同样的结果。218 个 issue 的子集与 RQ1 中 500 个 issue 的结果范围不同。

怎么看我们选取了 20 个灵犀解决、而去掉知识的版本没解决的 issue。两位作者对比了每个 issue 的两条轨迹，标出每个阶段起决定作用的知识维度（Cohen's κ = 0.66）。格子里的数字是该维度在该阶段起决定作用的 issue 数；每个阶段一列的总和为 20。

说明了什么分析阶段，根因分析步骤和相关架构占主导；规划阶段，设计模式与编码实践接手；修复阶段，修复模式和检查清单领先。总体来看，设计模式与编码实践最重要。

非方阵的 Hermite 标准形计算有误。

04 · 局限与展望

agent 遵循知识时，知识的作用最大。

500 个 issue 中仍有 127 个未解决。我们抽取了其中 20 个失败案例分析原因。在 15 个案例中，相关知识其实已经给到，但 agent 把它放在一边，按自己的推理行事（论文称为 uninformed autonomy）；在另外 5 个案例中，检索到的知识太少，不足以引导修复。知识以什么方式、在什么时机到达 agent，和恢复知识本身同样重要。

上限 · 理想选择器，并非系统结果
79.2%

如果在灵犀的分析之后采样三个补丁，并由一个理想选择器在存在通过的补丁时总能选中它，500 个中会有 396 个通过。灵犀并没有这样的选择器；这个数字表示补丁选择还有提升空间。

下一步
  • 把知识引导从分析阶段延伸到补丁生成。
  • 在 agent 的自主性和知识引导之间取得平衡。
  • 在 Python 之外验证：知识讲的是过程而不是语法，但 SWE-bench Verified 只覆盖 Python。
05 · 讨论

从论文到实践：代码从不记录的东西。

来自论文过程性知识，即 issue 怎么诊断、怎么修以及为什么，补上了当前代码无法呈现的东西。
