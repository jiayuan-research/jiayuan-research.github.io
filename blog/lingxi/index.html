Repository-Level Issue Resolution Framework Enhanced by Procedural Knowledge Guided Scaling

Experienced developers know something before they explore: how a kind of problem is diagnosed and fixed, and why. Lingxi recovers this procedural knowledge from a repository's own history and puts it in front of the coding agent, so that analysis, planning and fixing follow the procedure that fits the issue at hand.

01 · Motivation

Implicit knowledge tells developers where to look.

How does an experienced developer approach an issue? Before they explore, they already know something.

While learning and working, developers build up implicit knowledge: how a kind of problem is understood, analyzed and solved. A new problem rarely matches an old one exactly, so they draw a few shared patterns from many past cases, and together these patterns guide where they look first. Knowledge comes first; exploration follows.

An experienced developer

Draws on what past cases share

Many paths lead away from a slow page. The developer follows one, through the view and the ORM to the per-item queries, and rules out a side branch early. The numbered steps are the procedure; the why is what makes it reusable on the next slow page, even in a different codebase. That is procedural knowledge: how a kind of problem is diagnosed and fixed, and why. It is implicit: it lives in experience, not in the code.

Procedural knowledge

When a page loads slowly:

  1. 1Count the database queries
  2. 2Find the loop that issues them
  3. 3Confirm it in the query log

WHYper-item queries, the N+1 problem, are a common cause.

What today's agents miss

Not reliably, for two reasons.

Current agents are good at exploring in general. Two things keep that exploration from being guided by the procedure that fits the issue at hand.

Without task-specific direction ③ exploration

Knowing how to explore, but not how this issue is best explored

Models are trained on large amounts of code and already know, in general, how to explore a repository: search, read, reproduce, test. What they cannot know in advance is how this task is best approached in this repository: which practice applies, what to check first, and how the fix must fit the existing code.

Nothing ensures the right practice is recalled at the right moment, and private codebases were never in the training data. So gains come from more attempts: more samples, more retries. Coverage grows; direction for this issue does not.

In prior work: test-time scaling that samples many candidates and selects one, e.g. Trae, DARS, DEI.

At the surface procedural knowledge

Procedural knowledge missing, or history reused as raw data

Many agents use none: they work from the code and documents as they are now, which record the current state but not how similar issues were handled. Those that do draw on history reuse it as raw data: past issue reports and patches, retrieved as text. What was changed survives; the procedure behind it is lost: how the issue was diagnosed, and why this fix.

A copied change helps only when the new issue looks almost the same. The procedure behind it is what carries over.

What Lingxi doesLingxi recovers the procedure from the repository's own past issues and their patches, abstracts it so it transfers to similar issues, and, when a new issue arrives, puts the relevant pieces in front of the agent. The past fix is where the knowledge comes from; what the agent receives is the procedure.
02 · Method

Recover the procedure offline; guide every new issue.

Lingxi works in three phases. Phase 1 runs once per repository, over its history. Phases 2 and 3 run for each new issue: the retrieved knowledge first steers the analysis, then the planning and the fix.

1Phase 1 · offline knowledge construction

From issue-specific to transferable knowledge.

A past fix leaves only two things: the issue report and the final patch. The procedure in between is missing, so a knowledge agent recovers it in two steps. In Step 1 it reasons in reverse: it starts from the patch, navigates the repository snapshot where the issue occurred, and explains why each edit fixes the issue. In Step 2 it abstracts the result so that it transfers to issues that are similar but not identical.

Knowledge is built per repository from its own history; for each target issue, only issues created before it are used.

General root-cause analysis steps · same issue · step 2
  1. "Identify the request handling flow and URL resolution process
  2. Review how URL configuration is managed during request processing
  3. Analyze object creation patterns and resource usage
  1. Check for performance optimization opportunities like caching/memoization
  2. Verify thread-safety and resource cleanup mechanisms
  3. Test behavior with different URL configuration scenarios"

The issue: every request built a fresh URL resolver instead of reusing the cached one, wasting memory and time. Step 1 names the class and the memoized function that was bypassed. Step 2 turns this into a way to diagnose similar problems in any codebase: follow the request flow, look at which objects are created on every request, and check whether an existing cache is being bypassed.

2Phase 2 · knowledge-guided analysis scaling

One piece of knowledge per analysis agent.

A new issue arrives. Lingxi first summarizes it into four fields, then retrieves the knowledge of similar past issues: an embedding search keeps the top 20, a reranker orders them, and the three most relevant are kept.

Why one source per agent? Put all retrieved knowledge into one long prompt and the model tends to lose what is buried in the middle. Instead, each piece of knowledge guides its own analysis agent: three pieces, three agents, each following a different procedure and writing its own report. Analysis synthesis then keeps what is supportive, complementary, accurate and complete, and produces one consolidated analysis. The relevant knowledge is no longer left to recall; it is put in front of the agent.

Planning agent

Explore → reproduce → plan

A root-cause assessment and a line-level change plan, informed by the analysis and the issue-fixing knowledge. The agent explores the code, reproduces the issue, and links each planned change to the problem it addresses.

Fixing agent

Implement → test → refine

Apply the change, run the reproduction test, and refine until it passes: the final patch. The checklist tells it what to verify. Both agents work with four tools: directory view, file view, keyword search and a string-replace editor.

03 · Evaluation

Does it pay off, and which knowledge helps?

All experiments use SWE-bench Verified: 500 real GitHub issues from 12 open-source Python projects, each checked by hidden tests. Pass@1 is the share of issues whose single generated patch passes. For each target issue, knowledge comes only from issues created before it.

Experiments with commercial models completed before Sept 2025
RQ1 · overall effectiveness

With the same base model, Lingxi resolves the most issues.

How to readEach group uses one base model, so within a group only the framework differs. The baselines are the top leaderboard entries that use the same base model; multi-model ensembles are excluded.

What it showsWith Claude 4 Sonnet, Lingxi reaches 74.6%, 4.2 points above the strongest compared frameworks, OpenHands and Augment v1 (70.4%). With Kimi-K2, 70.3 versus 65.4. With GPT-4.1 mini, Lingxi nearly doubles mini-SWE-agent: 45.2 versus 23.9. Across groups, a stronger model lifts the same framework (the red line), and Lingxi is on top in every group. The knowledge adds to the model; it does not replace it.

How to readWhere does the gain come from: the knowledge, or the parallel agents? Each row removes or replaces one part of Lingxi. The 218 issues are a statistical sample (95% confidence, 5% margin of error).

What it showsWithout knowledge, Pass@1 is 67.4 to 67.7. Raw issue–patch pairs, the fix without the procedure, reach 68.3. Transferable procedural knowledge brings the largest step, to 74.8. Parallel analysis builds on that: with knowledge it adds 2.3 points, because each path follows its own piece of knowledge and the findings combine; without knowledge, parallel analyses of the same issue report land close to a single one. The two work together.

Differences are absolute percentage points; the paper's Table 3 reports the same results as relative Δ. The 218-issue subset is a different scope from the 500-issue results in RQ1.

04 · Limitations & outlook

Knowledge helps most when the agent follows it.

127 of the 500 issues remain unresolved. We sampled 20 of these failures and asked why. In 15, the relevant knowledge was available, and the agent set it aside and followed its own reasoning (the paper calls this uninformed autonomy); in 5, the retrieved knowledge was too sparse to steer the repair. How and when knowledge reaches the agent matters as much as recovering it.

Upper bound · oracle selector, not a system result
79.2%

If three patches were sampled after Lingxi's analysis and an oracle always picked a passing one when it exists, 396 of 500 would pass. Lingxi has no such selector; the number marks the headroom for better patch selection.

Next steps
  • Extend knowledge guidance from analysis into patch generation.
  • Balance agent autonomy with knowledge guidance.
  • Validate beyond Python: the knowledge is procedure rather than syntax, but SWE-bench Verified covers Python only.

Related plugin · Lingxi Advisor

Procedural knowledge for your coding agent

Lingxi builds its knowledge offline, which is not convenient day to day. Lingxi Advisor is a separate plugin built on the same idea: it brings procedural knowledge into everyday coding agents. Works with iCode and OpenCode.

Runtimeuse it

When the agent is unsure, it searches the procedural knowledge prepared for this repository and applies it, with sources.

Preparemine it

Derives procedural knowledge from a past issue and its patch, one at a time or in batches.
