SWE 智能体集成的补丁选择 · SWE-bench Verified

TestGRAD

演化测试套件，直到它能区分候选补丁

多个 SWE 智能体针对同一个 issue 会给出多个候选补丁，集成的效果取决于能否从中选对。TestGRAD 依据执行结果来选：它把仓库自身的测试套件当作被优化的对象，每轮更新一次，不断演化，直到有测试能把候选补丁区分开。

核心观点补丁选择就是测试空间优化。直接优化仓库的测试套件：让它瞄准候选补丁之间的行为差异，允许它读取、新建、更新和删除测试，并把反复出现的失败凝练成紧凑的动量，带入下一次尝试。
01 · 问题

补丁选择必须以程序行为为依据。

不同的 SWE 智能体各有所长：在某个 issue 上失败的智能体，在另一个 issue 上可能给出最好的补丁。集成方法让多个智能体处理同一个 issue，然后从它们的候选补丁中选出一个。

LLM 评审可以比较这些候选补丁，但没有执行证据时，它看到的是表面上的合理性，而不是补丁在仓库中的实际行为，而且容易受到补丁呈现顺序的影响。补丁选择应当基于测试：生成测试，在每个候选补丁上执行，再根据结果找出正确的补丁。难点在于得到真正能区分候选补丁的测试。

现有方法的不足

现有的测试生成方法是不完善的优化器。

02 · 方法

把测试套件的演化看作梯度下降。

TestGRAD 把仓库测试套件视为优化器的参数状态。

前向传播时，它在每个候选补丁上执行当前测试套件，检查补丁之间的行为是否不同。反向传播时，LLM 优化器把这一执行信号，连同从此前失败中挖掘出的动量，转化为对测试套件的下一次 CRUD 编辑。一旦有一个测试能区分候选补丁，或迭代预算用完，循环即结束。

1阶段 1 · 前向传播

在每个候选补丁上运行测试套件。

前向传播完全基于执行。TestGRAD 在每个候选补丁上运行当前测试套件 yt，记录通过或失败。只有当至少一个测试是差分测试，即在部分候选补丁上通过、在其余补丁上失败时，测试套件才对选择有用。结果一致（全部通过或全部失败）的测试不提供任何选择信号。

测试p1p2p3p4信号
test_a✓✓✓✓一致 · 无信号
test_b✕✕✕✕一致 · 无信号
test_c✕✓✕✓差分测试

怎么读行是测试，列是候选补丁；每个格子是一次执行，通过（✓）或失败（✕）。结果为示意。

说明了什么test_a 和 test_b 在每个候选补丁上结果都相同，无法帮助选择。test_c 在 p2 和 p4 上通过、在 p1 和 p3 上失败：有了它，测试套件就能区分候选补丁。

2阶段 2 · 差分损失

一旦有测试区分出补丁，损失即为零。

损失由执行结果定义，沿用差分测试的思路：不同执行之间的行为差异会暴露语义上的区别。它为优化器提供了明确的目标，也不同于现有流程在最终选择时采用的“数通过个数”。

TestGRAD · 差分损失

寻找行为上的差异

𝓛(yt) = 0 若 yt 含差分测试；否则为 1
𝓛 = 0优化停止。检查器智能体在循环之外、以独立的上下文只调用一次，利用差分结果选出最终补丁。 𝓛 = 1失败的更新成为下一轮迭代的优化信号。
对照 · 按通过数选择（Agentless、TRAE）

选通过测试最多的补丁

这种做法奖励的是“通过”，而不是“差异”。非差分测试仍可能偏向看似合理或测试不足的补丁，也没有任何机制推动生成器去找在不同候选补丁上结果不同的测试。

消融实验（RQ3）中，用这条规则替换差分损失和检查器后，Pass@1 从 84.2% 降到 80.8%。

3阶段 3 · 失败模式动量

把反复出现的失败挖掘为动量。

如果一次更新后测试套件仍是非差分的，说明这次更新没能区分候选补丁，TestGRAD 就把它写入失败记忆 M。它不重放每一条原始失败，而是从记忆中挖掘极大频繁失败序列：

mt = Mineβ(Mt−1 ‖ ∇t−1)

一个序列只有在至少 β 个失败测试套件中出现才会被保留（实验中 β 为 2）。得到的结果记录了哪些方向已经失败过，使下一次更新能避开同样的死路。与另调一次 LLM 写出的总结不同，它是确定性的，忠实于观察到的失败；与直接附加原始历史不同，它始终保持紧凑（RQ4）。

4阶段 4 · 反向传播

对仓库测试做一次完整的 CRUD 更新。

优化器接收损失、当前测试套件和动量，返回下一个测试空间梯度 ∇t = Optimizer(𝓛, yt, mt)，新的测试套件为 yt+1 = yt + ∇t。这个梯度是对原始仓库测试套件的一次编辑。现有流程大多只新建一个测试，最多再按名称删掉冲突的测试；而仓库测试往往依赖 fixture、初始化流程和辅助函数，其中的期望值也常常需要随修复一起改变。

优化器提示词 · 论文图 2（节选）

Given issue {I}, current test suite {y_t}, execution result {loss L(y_t)}, and momentum {m_t}:

  1. Explain why the current suite is still non-differential.
  2. Identify the failed direction preserved in momentum.
  3. Return one CRUD update over the original repository tests: [R]ead + Reuse, [C]reate, [U]pdate, [D]elete.

损失给出目标，动量指出已经失败的方向，因此更新会避开此前没有区分度的尝试。

四个更新方向
R
Read + Reuse（读取并复用） C/D 之外

收集仓库的测试知识：fixture、导入、断言工具和初始化约定。

C
Create（新建）

新增有区分度的测试。

U
Update（更新） C/D 之外

修改那些期望行为随修复而改变的过时断言或测试体。

D
Delete（删除）

只删除确认已过时的测试，而不是按名称匹配删除。

03 · 实验评估

在 SWE-bench Verified 上达到 84.2% Pass@1。

所有选择方法使用相同的候选补丁，只有选择模块不同。Pass@1 指每个实例选出一个补丁后，500 个实例中在 SWE-bench 评测框架下被解决的比例。单智能体基线（只用 Livesweagent）的解决率为 79.2%。

基准SWE-bench Verified

500 个经人工验证的 GitHub issue，在官方 SWE-bench Docker 镜像中运行。

候选补丁6 个排行榜提交

Livesweagent、Sonar、Trae_doubao、OpenHands、Gemini-Live、Atlassian，按此顺序依次加入（N = 1…6）。

基线Augment · Agentless · TRAE

不执行代码的 LLM 评审；Create/Delete 式测试生成；Create/Delete 加仓库浏览。

RQ1 · 整体有效性 · 4 个智能体的集成

在三个基座 LLM 上，Pass@1 均为最高。

怎么读每个面板中所有方法使用同一个基座 LLM，因此面板内只有选择方法不同。虚线是单智能体基线；每根横线从基线画到该方法的 Pass@1，旁边的小数字是相对基线的提升。

说明了什么TestGRAD 分别达到 84.2%、83.6% 和 84.0%，比单智能体高 4.4 到 5.0 个百分点，比各面板中最强的基线高 3.4 到 3.6 个百分点。TRAE 和 Agentless 最多只提升 1.4 和 1.2 个百分点。不执行代码、只做评判的 Augment 没有超过单智能体（−0.6 到 ±0.0）。

RQ2 · 集成规模 N = 1…6

各种规模下都领先 TRAE，N = 4 时最好。

怎么读智能体按上文所列顺序逐个加入。Oracle 指只要有一个候选补丁正确就算解决，Adversary 指所有候选补丁都正确才算解决，Expected 是随机选择；灰色带覆盖 Oracle 到 Adversary 之间的范围。蓝色竖条标出 N = 4，即 RQ1 使用的设置。

说明了什么当 N ≥ 2 时，TestGRAD 始终高于 TRAE；在 Minimax-m2.7 上，差距从 N = 2 时的 1.2 个百分点扩大到 N = 4 时的 3.6 个百分点。Pass@1 在 N = 4 时达到峰值，在 N = 5 和 6 时略有下降，此时加入的是较弱的智能体（Gemini-Live 77.4%、Atlassian 76.8%）。N = 4 时 Oracle 为 87.0%：还有 2.8 个百分点的差距，对应那些存在正确补丁、但生成的测试未能把它区分出来的实例。

RQ4 · 失败模式动量 · token 开销

动量让失败历史保持紧凑。

怎么读每轮优化迭代中失败历史上下文的平均 token 数，纵轴为对数坐标。原始记忆逐字附加每一个失败的测试套件；动量只保留挖掘出的频繁序列。斜体标注是第 4 和第 6 轮的压缩比（原始记忆 / 动量），与论文中的标注一致。

说明了什么原始记忆持续增长，在 Deepseek-v3.2 上到第 6 轮达到 16.4k token；动量则一直保持在几十到大约 150 个 token。压缩比在 Deepseek-v3.2 上超过 100×，在 GLM-5.1 上为 25–39×，在 Minimax-m2.7 上为 33–34×。去掉动量还会使 Pass@1 从 84.2% 降到 82.6%（RQ3）。
