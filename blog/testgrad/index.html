SWE-agent ensemble selection · SWE-bench Verified

TestGRAD

Evolving the test suite until it tells candidate patches apart

An ensemble of SWE agents produces several candidate patches for one issue, and it is only as good as its choice among them. TestGRAD makes that choice by execution. It treats the repository's own test suite as the object being optimized and evolves it, one update per iteration, until some test tells the candidate patches apart.

Take-homePatch selection is test-space optimization. Optimize the repository test suite itself: aim it at behavioral differences between the candidates, let it read, create, update and delete tests, and carry repeated failures forward as compact momentum.
01 · Problem

Selection must be grounded in behavior.

SWE agents have complementary strengths: an agent that fails on one issue may still produce the best patch for another. An ensemble runs several agents on the same issue and then has to select one of their candidate patches.

An LLM judge can compare the candidates, but without execution evidence it sees surface plausibility rather than repository behavior, and it can be sensitive to presentation order. Selection should be test-based: generate tests, execute every candidate patch, and use the outcomes to identify the correct one. The hard part is getting tests that actually tell the candidates apart.

Existing test generators are limited optimizers.

02 · Method

Test-suite evolution as gradient descent.

TestGRAD treats the repository test suite as the parameter state of an optimizer.

In the forward pass it executes the current suite on every candidate patch and checks whether their behaviors differ. In the backward pass an LLM optimizer turns this execution signal, together with momentum mined from earlier failures, into the next CRUD edit of the suite. The loop ends as soon as one test separates the candidates, or when the iteration budget is used up.

1Stage 1 · Forward pass

Run the suite on every candidate patch.

The forward pass is purely execution-based. TestGRAD runs the current suite yt against every candidate patch and records pass or fail. A suite is useful for selection only if at least one test is differential: it passes on some candidates and fails on others. Uniform outcomes, all pass or all fail, carry no selection signal.

What it showstest_a and test_b give the same result on every candidate, so they cannot help choose. test_c passes on p2 and p4 and fails on p1 and p3: with it, the suite separates the candidates.

2Stage 2 · Differential loss

The loss is zero once a test separates the patches.

The loss is defined by execution, following the differential-testing intuition that behavioral differences across executions expose semantic distinctions. It gives the optimizer an explicit target, and it is different from the pass counting that existing pipelines use for the final choice.

TestGRAD · differential loss

Search for behavioral contrast

𝓛(yt) = 0 if yt contains a differential test; 1 otherwise
𝓛 = 0Optimization stops. A checker agent, invoked once outside the loop with a separate context, uses the differential result to select the final patch. 𝓛 = 1The failed update becomes the optimization signal for the next iteration.
Contrast · pass-count selection (Agentless, TRAE)

Pick the patch that passes the most tests

This rewards passing, not contrast. Non-differential tests can still favor broadly plausible or under-tested patches, and nothing drives the generator toward a test whose outcome differs across candidates.

In the ablation (RQ3), replacing the differential loss and checker with this rule lowers Pass@1 from 84.2% to 80.8%.

3Stage 3 · Failure Pattern Momentum

Mine repeated failures into momentum.

If an update leaves the suite non-differential, it has failed to separate the candidates, and TestGRAD writes it into failure memory M. Instead of replaying every raw failure, it mines maximal frequent failure sequences from that memory:

mt = Mineβ(Mt−1 ‖ ∇t−1)

A sequence is kept only if it appears in at least β failed test suites (2 in the experiments). The result records which directions have already failed, so the next update can move away from the same dead end. Unlike a summary written by another LLM call, it is deterministic and faithful to the observed failures; unlike appending the raw history, it stays small (RQ4).

4Stage 4 · Backward pass

A full CRUD update to the repository tests.

The optimizer receives the loss, the current suite and the momentum, and returns the next test-space gradient, ∇t = Optimizer(𝓛, yt, mt); the new suite is yt+1 = yt + ∇t. The gradient is an edit over the original repository test suite. Existing pipelines mostly create a test and, at most, delete conflicting ones by name; repository tests often depend on fixtures, setup routines and helpers, and on expected values that must change with the fix.

Optimizer prompt · Figure 2 of the paper, abridged

Given issue {I}, current test suite {y_t}, execution result {loss L(y_t)}, and momentum {m_t}:

  1. Explain why the current suite is still non-differential.
  2. Identify the failed direction preserved in momentum.
  3. Return one CRUD update over the original repository tests: [R]ead + Reuse, [C]reate, [U]pdate, [D]elete.

The loss sets the target and the momentum names the direction that already failed, so the update moves away from previous non-discriminative attempts.

The four update directions
R
Read + Reuse beyond C/D

Collect the repository's testing knowledge: fixtures, imports, assertion utilities, setup conventions.

C
Create

Add new discriminative tests.

U
Update beyond C/D

Revise stale assertions or test bodies whose expected behavior changes with the fix.

D
Delete

Remove only tests confirmed obsolete, rather than deleting by name matching.

03 · Evaluation

84.2% Pass@1 on SWE-bench Verified.

All selection methods receive the same candidate patches and differ only in the selection module. Pass@1 is the fraction of the 500 instances resolved under the SWE-bench harness after one patch is selected per instance. The single-agent baseline, Livesweagent alone, resolves 79.2%.

RQ4 · Failure Pattern Momentum · token cost

Momentum keeps the failure history compact.

How to readAverage tokens of failure-history context per optimization iteration, on a log scale. Raw memory appends every failed test suite verbatim; momentum keeps only the mined frequent sequences. Italic labels are compression ratios (raw / momentum) at iterations 4 and 6, as labelled in the paper.

What it showsRaw memory keeps growing, to 16.4k tokens by iteration 6 with Deepseek-v3.2, while momentum stays between a few dozen and about 150 tokens. The ratio exceeds 100× with Deepseek-v3.2 and is 25–39× with GLM-5.1 and 33–34× with Minimax-m2.7. Removing momentum also lowers Pass@1, from 84.2% to 82.6% (RQ3).
